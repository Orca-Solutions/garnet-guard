# Garnet Guard: instructions for coding agents

`AGENTS.md` and `CLAUDE.md` are identical copies and must stay identical. Codex reads `AGENTS.md`; Claude Code reads `CLAUDE.md`. If the maintainer's private operating guide (`SOFTWARE_OPERATING_GUIDE.md`, `PR_WORKFLOW.md`, `docs/AGENT_ROLES.md`) is present in your workspace, follow it as well; it is supplied through project instructions, not the repository. Report unavailable guidance instead of claiming it was checked.

## Commands

- Install: `uv sync`
- Dev server: none (CLI and GitHub Action)
- Focused tests: `uv run pytest tests/<path> -k <name>`; all unit tests: `uv run pytest` (no network); network tests only when asked: `uv run pytest -m network`
- Lint / typecheck: `uv run ruff check . && uv run ruff format --check . && uv run mypy src && uv run lint-imports`
- Build: `uv build`
- Backtest (required for rule changes): `uv run python -m backtest`

Run tests, ruff and mypy before saying a change is done.

## Project-specific

### What Garnet Guard is

A release-diff guard for dependency updates. It compares a new version of a package against the version a project already trusts and reports trust downgrades, risky content changes and known-bad matches.

### Hard rules

These are not style preferences. A change that breaks one is wrong even if tests pass.

1. **Never execute inspected package code.** No `import`, `exec`, `subprocess`, build backend or install of anything Garnet downloads. Parse with `ast` and read files as bytes.
2. **All archive access goes through `safe_archive.py`.** Never call `zipfile`/`tarfile` extraction elsewhere.
3. **Checks are pure.** No I/O in `checks/`. Fetching belongs in `ecosystems/`. Respect the import rules in docs/API.md §2.
4. **"Couldn't check" is never "pass".** Errors surface as findings or a non-zero exit.
5. **Escape all package-supplied strings** before they reach markdown, SARIF or a terminal.
6. **Rule IDs are permanent.** Don't renumber or reuse them.
7. **No new runtime dependency** without an ADR in `docs/decisions/`. Dev dependencies are fine.
8. **Unit tests use fixtures, not the network.**
9. **Never weaken a test, skip a test or lower a backtest threshold to get green.**

### High-risk paths

These are Garnet Guard's high-risk class: changes to them get focused independent review and the maintainer's deliberate review. Call them out at the top of the PR description.

- `src/garnet_guard/safe_archive.py` and `src/garnet_guard/net.py`
- `action/` and `.github/workflows/`
- release and publishing configuration
- default policy and rule severities

Other routine changes are verified by their author.

### How work flows

- Work happens on a branch, one issue per branch, and lands through a pull request. Agents open PRs as drafts; only the maintainer merges.
- Keep PRs small. If a task grows, stop and propose a split in the PR description.
- A PR that adds or changes a rule includes positive and negative fixtures, `garnet explain` text and the backtest delta.
- If a requirement is unclear, leave a question in the PR rather than guessing at behavior users will see.
- Commits are signed (configured signing) and signed off (`git commit -s`, DCO).
- **No co-author trailers or "generated by" lines in commits.** The commit-msg hook strips them. Disclose agent use in the PR description's "AI assistance" section instead.

### Style

- **User-facing text** (findings, `explain` text, PR comments, CLI messages) follows the voice rules in docs/brand/brand-kit.md: calm, exact, never "safe", evidence on every line.
- Python 3.11+, full type hints, `mypy --strict` on `src/`.
- Dataclasses (frozen) for models. Keep the public API in `garnet_guard/__init__.py` small.
- Findings must be deterministic: sort output, avoid timestamps in report bodies.
- Error messages and `explain` text are written for a developer reviewing a dependency PR: say what changed, why it matters, and what to do.
