## 2026-10-31: requirements files: index options apply to the whole file

**State.** `lockfiles/requirements.py` `parse()` applied a private `--index-url` or `-i` only to the lines after it, and matched only `-i ` and `--index-url` at the start of a line. pip applies index options to every requirement in the file (they set the finder before any requirement is resolved), reads options with optparse, so any unambiguous prefix of a long option and a short option's attached value count (`-ihttps://…`, `--index=…`, `--extra-ind URL`, `-f/dir`, `--find-l=/x`, `--no-ind`), and never looked at `--extra-index-url`, `--find-links` or `--no-index` here at all. So a pin could be checked against PyPI while pip installed it from another index. `parse()` now splits each line as pip's `break_args_options` does, reads the options against the requirements-file option table of pip 24.0 (with 26.2's additions, so an abbreviation ambiguous there isn't taken as one option), and makes a file-wide decision: when the file sets an index other than PyPI, an extra index other than PyPI, `--find-links` or `--no-index`, or holds an option pip would refuse (unknown, ambiguous, a flag given a value, a missing value, a quote shlex can't close), every `==` pin in it is GRN-E005 with a reason that names the option, never its value. `-r` and `-c` files are followed (second commit, after the coordinator asked for it instead of treating every include as unknown): `workspace.requirement_includes` walks each requirements lockfile's include tree through a reader (`disk_reader` for the working tree and the `--base` file's folder, `git_reader` for `--git-base`, which checks the `ls-tree` mode so a symlink at the base is refused), resolving each path beside the file that names it as pip does. It follows only paths inside the directory `garnet check` runs in, never a symlink (`plain_file`), at most `MAX_INCLUDE_DEPTH` = 10 deep, and stops at a cycle; a URL, `file:`, an environment variable, an absolute or escaping path, a missing, non-UTF-8 or over-64-MiB file can't be followed. The index options of a whole tree apply to every pin in it: to the including file's pins (an index set in `base.txt`) and to the included lockfile's pins (an index set in `requirements-dev.txt` applies to `base.txt` when both are checked). An include that can't be followed is GRN-E005 for the pins of its tree. The parser stays pure: the walk lives in `workspace.py` and hands `parse` an `Included` (reason and compared-only origin); without one, as from the install wrapper and `garnet diff`, a file with an include stays GRN-E005. The existing GRN-E005 path (`Pin.source = "unsupported"`) is extended; no new rule. The index values are kept in `Pin.origin`, which is compared and never shown, so a change of index counts as a change. Unpinned lines stay GRN-E004. Attached and long editables (`-e.`, `--editable=./x`) are now reported as editable installs; before, a line starting `-e.` was skipped. The rule page, SPEC §3.1 and `garnet explain GRN-E005` (770 characters) say so. Nothing in backtest facts changed; CACHE_FORMAT is unchanged.

Review fixes (third commit), each checked against pip 24.0's parser with the reviewer's probes: `logical_lines` now copies pip's `join_lines` then `ignore_comments` (join with nothing between after `strip("\\")`, no continuation from a comment line, comments stripped after joining), so `--\\` + `index-url …` and `\\--index-url …\\` + a blank line read as index options; the install wrapper's requirements reading uses the same function, so it changed too. An include path with a `..` part is never followed (`link/../x.txt` through a symlinked folder named a file outside it once normpath folded it). An option pip would refuse is shown only by its leading run of dashes and letters, cut to a known option when one starts it (`--extra-index-url…`) or to 24 characters, so a glued credential can't reach the report. Each include path is read once per run, and one tree stops at 100 include lines or 64 MiB read, which leaves its pins GRN-E005. `disk_reader` resolves a relative root first (it doubled the path). The rule page lists what isn't seen: `PIP_INDEX_URL` and friends and `pip.conf`, several files on one pip command line, `${VAR}` expanding to an option.

**Open tasks.** Backtest delta pending (`backtest/` doesn't import the lockfile parsers, so none is expected). The pins of an included file that isn't itself a discovered lockfile (`base.in`, `constraints.txt`) are still not checked, as before; only its options count. With `--base PATH`, the base's includes are read from disk beside that file, as they are now, not as they were. The include walk and the install wrapper's `_read_file` could share code. The install wrapper's own option table (`install/pip.py` `_FILE_OPTIONS`) lacks `--pypi-url` and pip 26's additions; it refuses unknown options, so that is not a gap, but the two tables could be shared.

## 2026-10-30: Install wrapper and agent hooks (pip and uv)

**State.** `garnet pip install …`, `garnet uv add|remove|lock|sync …`, `garnet hook claude-code|codex` and `garnet hook <agent> run` are built, in `src/garnet_guard/install/`, as SPEC §10.3 and §10.4 now describe them ([docs/install-wrapper.md](docs/install-wrapper.md)). The design follows the 2026-10-30 research brief: pip and uv run build backends while resolving, so the resolve step turns builds off and refuses what would turn them back on; with builds off they fall back silently to an older release, so each requested package is compared with its newest matching PyPI release and that case is "can't check", exit 3. The hand-off installs exactly what was checked (pip with hash-pinned constraints, uv with `uv sync --frozen` after a hash-checked write-back). The hooks answer with context, deny, or ask (Claude Code) / deny (Codex). The entry point moved to `garnet_guard.console:main` so the hook's fast path imports only the standard library (about 35 ms instead of about 800 ms with the engine), and `garnet_guard/__init__.py` loads its names lazily. Two import-linter contracts were added. SPEC §3.3, §10.1, §10.3 and §10.4 were rewritten and ADR-0005 amended; both wait on the maintainer. - npm names are kept as written and checked against npm's rules (optional `@scope/`, URL-safe characters, at most 214, no leading `.` or `_`, no `..`, no other slash). `ecosystems/npm.normalize` now uses the same check, so a name a parser passes is one the registry adapter accepts; it was stricter (first character a letter or digit, no `~!*'()`), so a valid legacy name from a lockfile would have raised inside `evaluate`. `registry_url` already percent-encodes the name into one path segment. A registry `resolved` URL (registry.npmjs.org or registry.yarnpkg.com) must be `/<name>/-/<unscoped>-<version>.tgz` for the entry's own name and version, else GRN-E005 "resolved URL isn't this package's registry tarball": otherwise a lockfile could name one package and install another, and Garnet would check the wrong one. The version must be SemVer, so it can't walk the path to another tarball (`2.1.3/../../../evil/-/evil-1.0.0`). An entry with a SemVer version and an integrity but no `resolved` counts as the default registry. Git, `file:`, `http://`, other tarball URLs and private registries are GRN-E005; details never quote the URL, which can carry a token. `Pin.origin` records the URL and the integrity, so a git dependency moved to another commit at the same version, or a new tarball behind the same URL, is reported again.

A flagged entry with a URL or integrity is judged by that source: npm fetches it from its own `resolved` when the parent's tarball doesn't hold it (Arborist's `#bundleMissing`), and npm writes neither for a dependency it found in a tarball (unless npm 6 or earlier left `_resolved` in that dependency's package.json, in which case it is checked as that source says, a registry release included). The project's own `bundleDependencies` install from the registry and are checked. In yarn.lock, an entry is skipped only when every pattern is `link:`; yarn installs the other patterns of a mixed entry from its `resolved` URL, so they are judged as usual. Every package counts, dev, optional and peer included.
- package-lock.json: `packages` and `dependencies` are both read whenever they are there, whatever `lockfileVersion` says: Arborist installs from `packages` when it exists (it migrates `dependencies` only `if (data.dependencies && !data.packages)`), and npm 6 installs from `dependencies` and ignores `packages`. A `dependencies` entry is compared with the `packages` entry at the same install location (a link's own dependencies sit under its target, as Arborist places them) and reported as well unless both install the same thing: the same URL and integrity, the same registry release, or a link written as `file:`. On three lockfileVersion 2 files written by npm 10.9.4 (a project with npm@10.8.3, 662 packages of which 200 bundled, and a URL alias; two workspaces with `file:` folders, a `file:` tarball and dependencies nested under links), the `dependencies` section adds nothing.
- yarn.lock is read with a port of Yarn 1's tokenizer and parser (yarn 1.22.22 `lib/cli.js`), so Garnet sees what yarn sees. Yarn reads a file its own parser throws on as YAML, stops at a line indented deeper than it expects and ignores the rest, and merges both sides of merge conflict markers; Garnet refuses all three with exit 3, as it does a `__metadata` entry (Yarn 1 then ignores the lockfile), a top-level value that isn't an entry (yarn reads it as a pointer to another pattern), a `version`, `resolved` or `integrity` that isn't a string, and a `yarn lockfile v<N>` comment above 1. The old line-based reader skipped every 4-space line, so `  version:` / `    "2.1.3"` gave yarn a version and a `resolved` URL Garnet never saw. On an 8 MB yarn.lock of 25,000 entries the port takes about 1.7 s (the line reader took 1.2 s).
- Strings from JSON escapes that aren't valid text (a lone `\ud800`), in package-lock fields and keys and in yarn's quoted strings, are a `LockfileError`; they crashed the text and markdown output. The text report now escapes a line break in any field as `\x0a` (it already did for markdown and SARIF); uv.lock reached that on main too.
- Each pin's line is its package-lock key (found by following the JSON tokens, since `json` has no positions) or its yarn `version` line. Errors name the lockfile and a position, never the file's text, and say "(in the base version)" for the base. Nesting past 256 levels (Garnet's own limit: Python 3.14's depends on the stack size, and CI's 3.14 runner parsed 100,000 levels), non-object values, `node_modules/../x` keys, wrong field types, invalid UTF-8 and files over 64 MiB (a new cap, for every format) are `LockfileError`, exit 3.
- `discover` adds package-lock.json, npm-shrinkwrap.json and yarn.lock after the Python files, and leaves out a Yarn 2+ yarn.lock; pnpm-lock.yaml isn't looked for. A yarn.lock counts as Yarn 2+ only when it has no Yarn 1 header and its first entry is `__metadata:` with `  version: ` under it, the shape Yarn 1 ignores (it discards a lockfile whose `__metadata` is truthy); an empty `__metadata:` reads as null under the YAML fallback, and Yarn 1 installs from such a file, so it is read, and refused for its missing header. With `--git-base`, a left-out yarn.lock whose base version isn't Yarn 2+ is refused with exit 3: the switch can come with any change to what installs. Either format passed with `--head` is a `LockfileError`. `action/run.sh`'s auto list, which it checks for symlinks, gained the same three names; nothing else under `action/` changed, and a test now checks the list against `discover`'s names.
- Policy: ignores already matched npm names exactly. `--policy-change` compared ignore names PEP 503 normalized for every ecosystem, so moving an npm ignore from `foo_bar` to `foo-bar` went unlisted; only `ecosystem = "pypi"` ignores are normalized there now. `versions` stays PEP 440 only and never matches an npm change.

## 2026-10-29: policy file and ignores

**State.** The SPEC §7 policy is built in `src/garnet_guard/policy.py` and applied by the engine:

- `garnet.toml`, or `[tool.garnet]` in `pyproject.toml`, with `version = 1`, `default`, `fail_on`, `[garnet.rules]`, `[[garnet.ignore]]` and `[garnet.limits]`. Unknown keys, unknown rules, raised limits and ignores without `reason` or `until` are errors (exit 3).
- `garnet check` and `garnet diff` read it (`--policy PATH`, `--no-policy`); `--fail-on` now defaults to the policy's `fail_on`, else `block`. `garnet policy check [PATH]` validates one and lists its ignores.
- An ignored finding keeps its severity and stays in every output (`suppressed_by` in JSON, `ignored` in text, "ignored by the policy" in the comment) but doesn't count toward the verdict. An ignore applies through its `until` date; afterwards the finding counts again with a note, and the report lists expired ignores (`policy.expired` in JSON, a line in the comment).
- GRN-T007, T008 and K001 can't be lowered in `[garnet.rules]` and need `acknowledge_critical = true` in an ignore. GRN-E001 to E005 can't go below their default in `[garnet.rules]` or via `default`, so a check that didn't run never passes quietly; a per-package ignore still can.
- The Action gained a `policy` input (`auto`, or a path). `action/run.sh` reads it from the base commit with `git show`, so a pull request can't relax its own policy, and passes `--no-policy` when the base has none. The `fail-on` input default is now empty (the policy's `fail_on`, else `block`).
- `docs/policy.md` is the user guide; the 20 rule pages link to it instead of saying 0.1 doesn't read policies.

**Verification.** `uv run pytest` (198 tests, 65 of them in `tests/test_policy.py` and 8 new Action tests), ruff, mypy (strict) and `lint-imports` (a new contract keeps `policy.py` off the network and archives) pass. `uv run python -m backtest`: unchanged, the three incidents are caught (lightning 2.6.2 and 2.6.3 by GRN-C003 and T004, elementary-data 0.23.3 by GRN-C001 and T004) and 0 of 20 clean updates warn.
