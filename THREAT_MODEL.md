# Garnet Guard threat model

Garnet is a security tool that downloads hostile files and runs with write access to pull requests. This document says what Garnet defends against, what it doesn't, and how Garnet keeps from becoming the attack vector.

## Part 1: what Garnet detects

### Attacker we target

Someone who gains the ability to publish a new version of a **legitimate, already-trusted package**, by any of:

| Path | Example | Garnet signals |
|---|---|---|
| Stolen or leaked long-lived publish token | lightning 2.6.2/2.6.3, litellm 1.82.7/1.82.8, telnyx 4.87.1/4.87.2, ultralytics 8.3.45/8.3.46, xinference 2.6.0–2.6.2, durabletask 1.4.1–1.4.3 | Lost provenance (T001), outside Trusted Publishing (T005), no matching tag (T004) |
| Hijacked maintainer account (phishing, session theft) | num2words 0.5.15/0.5.16, July 2025; chalk/debug, Sept 2025 | No matching tag (T004) for all four; new import-time exec (C003) for num2words. Lost provenance (T001) and a new install script (C002) cover the same path when the trusted release was attested or the payload is an install script |
| Compromised CI of the real project (script injection, poisoned action or cache, pushed release tag) | elementary-data 0.23.3, ultralytics 8.3.41/8.3.42, memoryos 2.0.34 | Provenance looks valid, so content rules carry it: new `.pth` (C001), changed build backend (C002), new import-time exec (C003), code that isn't at the tag (C007, ultralytics 8.3.42) |
| Moved publishing to a fork or new repo | repo-jacking variants | Publisher changed (T002), workflow changed (T003) |
| Known-bad release already listed | any feed-confirmed case | OSV `MAL-` match (K001) |

The design bet: an attacker can fake a lot, but it is hard to fake *both* "same publisher identity as last time" *and* "content changes that look like a normal release".

### Out of scope

- **Malicious first versions** of new packages, typosquats and slopsquats. Cooldowns and malware feeds cover these; Garnet can still report K001 if a feed has it.
- **Long-standing malicious code** that was already in the baseline. Garnet trusts the baseline by definition.
- **A compromise that changes nothing Garnet looks at:** a valid attestation from the real workflow, a matching tag, and a malicious change that reads like normal code in a non-import-time path. Garnet lowers risk; it does not prove safety. Reports must never say "safe".
- **Registry or Sigstore compromise.** Garnet relies on PyPI, npm and Sigstore being honest about what they serve and sign.
- **Runtime behavior.** No sandbox, no dynamic analysis.

### Evasion

Rules are public, so attackers can read them. Responses:

- Lean on trust signals that require control of the real publisher identity, not on content patterns alone.
- Rules run on *changes*, so hiding a payload means making it look like an ordinary diff, which raises the cost.
- Novel bypasses are reported privately (see [SECURITY.md](SECURITY.md)) and land with a backtest fixture.

### Known gaps and the plan

A red-team pass on 2026-10-30 listed the ways a malicious release could still get past the rules. This is the condensed map: what each gap is, what Garnet sees of it today, and the issue that closes it. The order and phase of each fix are in [ROADMAP.md](ROADMAP.md#closing-the-evasion-gaps). Ideas already public are tracked here and in ordinary issues; a bypass nobody has published yet still goes through private reporting.

| A startup file other than `.pth`: `sitecustomize.py`, `usercustomize.py`, files under `.data/` | GRN-C010 new-startup-file warns for a new `sitecustomize` or `usercustomize` module (source, package, `.pyc` or extension, in any case, also under `.data/`), a script named like a common command and a file installed under `etc/`, and lists other new scripts and data files at `info`. Wheels only: what an sdist installs is up to its build | Done: [#49](https://github.com/orca-solutions/garnet-guard/issues/49) |
| An import hook installed at import (`sys.meta_path`, `settrace`, `builtins`, metaclasses) | Only when the call is on the sensitive list | Hook installation [#55](https://github.com/orca-solutions/garnet-guard/issues/55) |
| The real release workflow, run from a different branch, ref or trigger | Provenance looks normal; the ref and trigger aren't compared | Different ref or trigger [#56](https://github.com/orca-solutions/garnet-guard/issues/56); release-workflow diff at `info` [#57](https://github.com/orca-solutions/garnet-guard/issues/57) |
| The attacker also pushes a matching tag | GRN-T004 is satisfied | Tag sanity checks [#61](https://github.com/orca-solutions/garnet-guard/issues/61) |
| The bad release is between the trusted version and the candidate | Trust rules compare the two ends only | Intermediate releases, SPEC §5.2 [#62](https://github.com/orca-solutions/garnet-guard/issues/62) |
| The payload sits in a model or data file a loader runs (pickle) | Nothing | Model loaders [#59](https://github.com/orca-solutions/garnet-guard/issues/59) |
| An ignore added to the policy in the same PR as the update | The Action checks the pull request with the base commit's policy, so the new ignore doesn't apply to it, and the comment lists the edit, loosening changes first. After the merge it applies to every later pull request, for at most 12 months | Done: policy guardrails [#51](https://github.com/orca-solutions/garnet-guard/issues/51) |
| An update that never reaches a lockfile (installed by hand, or in an image) | Nothing: Garnet checks lockfile diffs | A scheduled check of a deployed environment [#63](https://github.com/orca-solutions/garnet-guard/issues/63) |
| A risky property added slowly, one small step per release | Each step is compared only with the release before | Per-package history, v2 [#64](https://github.com/orca-solutions/garnet-guard/issues/64) |

Smaller notes that help a reviewer without a new rule are done ([#50](https://github.com/orca-solutions/garnet-guard/issues/50)): a change whose trusted release has no attestation and no git tag says that GRN-T001 to GRN-T005 had nothing to compare with, GRN-C003 lists new reads of credentials and CI settings at import at `info`, and the remediation text points at the repository before the release notes, which whoever published the release also wrote.

## Part 2: protecting Garnet itself

### Assets

- The CI environments and developer machines that run Garnet.
- The `GITHUB_TOKEN` and any tokens the Action receives.
- The integrity of Garnet's verdicts. A forged "pass" is the worst outcome.
- Garnet's own release pipeline on PyPI and the Action's repository.

### Threats and mitigations

| Threat | Mitigation |
|---|---|
| A hostile package exploits Garnet's parser (zip bomb, path traversal, symlink, huge file, pathological AST) | All archive access goes through `safe_archive.py` with size, ratio, count and depth limits. No links or device files. `ast` parsing has size and time limits. The git packfile reader (`ecosystems/gittree.py`) caps the response, each object and their total, verifies the pack checksum and bounds every delta. Fuzz tests on the archive and lockfile parsers. |
| Garnet executes package code by accident (importing a module, running a build backend to get metadata) | Hard invariant: no execution. Metadata comes from the registry and static files (`METADATA`, `pyproject.toml`, `package.json`). A test asserts no subprocess or import of inspected content. |
| A malicious PR abuses the Action (pwn request) | No `pull_request_target` with PR checkout. Least-privilege tokens. Comments are posted from a job that never executes PR content. Report text from packages is escaped in markdown. |
| Markdown or terminal injection via package names, file names or metadata | Every string from a package is escaped before rendering in comments, SARIF and terminals. |
| A pull request's lockfile names one package but installs another (an npm alias, a `resolved` URL for a different tarball, a section or a syntax that one installer reads and Garnet doesn't), or carries a name built to change a registry URL | An alias is checked as the package it installs. A registry `resolved` URL must be that package's tarball for that version; any other URL, and git, path, private-registry and bundled entries, are GRN-E005. A bundled entry with a URL or integrity of its own is judged by that source, since npm fetches it from there when the parent doesn't ship it. Both sections of a package-lock.json are read, since npm 7 and later install from `packages` and npm 6 from `dependencies`. yarn.lock is read with a port of Yarn 1's parser, and a file Yarn 1 would read another way (as YAML, only in part, or merged from conflict markers) is refused. A name that breaks npm's naming rules is GRN-E005, never reaches a URL and isn't echoed in the report; a valid name is percent-encoded into one path segment. Garnet fetches by name and version from the registry, never from the lockfile's URL. |
| A pull request's pnpm-lock.yaml or Yarn 2+ yarn.lock is YAML that Garnet reads differently from pnpm or Yarn (both use js-yaml, a YAML 1.2 parser), or that blows up when read (aliases, deep nesting, a huge file) | `lockfiles/yamldoc.py` (ADR-0016) builds the document from PyYAML's parser events and never runs a loader, so no tag can build an object and no alias is followed. Aliases, anchors, tags outside the core schema, merge keys, repeated keys (as js-yaml compares them), keys that aren't scalars, a second document, nesting deeper than 32 levels and NEL, LS and PS are refused with exit 3. Plain scalars are typed as js-yaml types them, and one that YAML 1.1 and 1.2 read differently is never taken as text. Lockfiles over 64 MiB are refused before parsing. Errors give a line and column, never the file's text. In pnpm-lock.yaml each snapshot is checked as the `packages` entry pnpm installs it from, and a snapshot with its own resolution, name or version, or with no `packages` entry, is refused. A Yarn 2+ `patch:` and a pnpm `patchedDependencies` entry are checked as the release they patch, and a patch file from outside the project (absolute, on a Windows drive, with a backslash, or out of the lockfile's folder) is GRN-E005, a Yarn 2+ one even when it patches the project's own code; Yarn 2 and 3 patch paths are read with their own grammar (`~builtin<...>`, no `~/` project paths). A yarn.lock counts as Yarn 2+ only in the shape Yarn 1 ignores, so a file Yarn 1 would install from is always read as Yarn 1's, and the registry settings are read for the same decision the parser makes. |
| pnpm-lock.yaml and Yarn 2+ yarn.lock don't record the registry, so the project's configuration can send a package to a private registry, where the same name and version isn't the public release Garnet checks | Garnet reads the `registry` and `@scope:registry` keys of the .npmrc beside a pnpm-lock.yaml, as pnpm 10's `ini` 1.x parser reads them (a section header only when the line is exactly `[name]`, lines split only at CR and LF, a byte order mark trimmed, a scope up to the key's first colon), and the `registries` table of the pnpm-workspace.yaml there (pnpm 10 takes it over .npmrc's; a package either file sends elsewhere counts), and `npmRegistryServer` and `npmScopes` of the .yarnrc.yml beside a Yarn 2+ yarn.lock. A package they send anywhere but registry.npmjs.org or registry.yarnpkg.com, or to a registry named by an environment variable, is GRN-E005 "private registry, set in <file>". pnpm also expands environment variables in .npmrc keys and in pnpm-workspace.yaml's top-level keys, with a fallback the file can supply (`${X:-registry}`), so such a key counts as every registry key it may be read as. Nothing else in those files is read, and nothing from them is shown, since they can hold tokens; a symlinked, oversized or unreadable settings file is refused like a lockfile. The YAML reader's refusals apply to the keys read and to the top-level keys' names; other values (a pnpm catalog with anchors) are passed over. A `@jsr/` package, which pnpm and Yarn 4 fetch from npm.jsr.io by default, is GRN-E005 unless .npmrc or pnpm-workspace.yaml sets npm's public registry for `@jsr`, or .yarnrc.yml configures the `jsr` scope. Residual risk: settings Garnet can't see (environment variables such as `npm_config_registry` or `YARN_NPM_REGISTRY_SERVER`, the user's home folder, a parent folder) aren't applied, so such a package is checked as npm's public release of that name. The lockfile's integrity isn't compared with the public release's yet; the package manager compares it at install. |
| Network attacker tampers with downloads | HTTPS only. Downloaded files are checked against the registry's published hashes before inspection. |
| Garnet's own dependencies are compromised | Small dependency set. Hash-pinned lock (`uv.lock`) in CI and releases. Garnet runs Garnet on its own dependency PRs. New runtime dependencies require an ADR. |
| Garnet's release is hijacked | PyPI Trusted Publishing from a protected environment with required reviewer, PEP 740 attestations on every file, signed tags, 2FA and hardware keys on maintainer accounts, no long-lived publish tokens. |
| The Action repo is tampered with | Users pin by commit SHA in docs. Branch protection and signed commits on main. Release tags are immutable. |
| AI agents introduce a subtle weakness | Agents never merge. Changes to `safe_archive.py`, the Action, release workflows and policy defaults require a careful human review (see [AGENTS.md](AGENTS.md)). |
| An upstream outage silently weakens results | "Couldn't check" is reported as an error finding, never as pass. |
| The install wrapper or a hook runs a package's build code while checking (pip prepares sdist metadata during `--dry-run`; uv builds sdists with dynamic metadata) | The resolve step turns builds off: pip gets `--only-binary :all:` after every user argument, after Garnet has read every requirements file and refused `--no-binary`, editable, path, URL and VCS lines; uv gets `--no-build` and `UV_NO_BUILD=1`, and its `--build`, editable and local sources are refused, in `[tool.uv.sources]`, uv's `-r` and `-c` files and the dependency tables' direct references; after the resolve, any non-index package in the new `uv.lock` is can't check. Local archive names are read as pip reads them (markers and extras taken off first, pip's whole extension list, `.tar.lzma` included). uv also gets `--no-python-downloads` and `UV_PYTHON_DOWNLOADS=never`, because a project's `[tool.uv]` can point Python downloads at an interpreter of its choosing, which uv runs. pip runs as `<python> -I -m pip`, so a `pip/` folder in the working directory isn't imported. Tests run real pip and uv offline against sdists whose build backend doesn't exist, and uv against a fake Python download. |
| The npm wrapper or a hook runs package code while resolving or installing | npm resolves with `--package-lock-only --ignore-scripts` in a private copy of `package.json`, the lockfile and `.npmrc`. That isn't enough on npm 10: a git-host dependency pinned to a full commit is packed to read its manifest, which runs its `prepare` script whatever `--ignore-scripts` says (pacote 19; a canary test shows it). So the resolve also gets `npm_config_script_shell` and `npm_config_git` pointing at programs that don't exist (any script or git command fails, and the command is can't check), and npm 11's `--allow-git=none`, `--allow-remote=none`, `--allow-file=none` and `--allow-directory=none`. Git, URL, file and folder specs on the command line, in package.json's dependency tables and in `overrides`, workspaces, and options and npm settings Garnet doesn't know are refused before npm runs; after the resolve, any lockfile entry npm wouldn't fetch from a registry, and any link, is can't check, because `npm ci --ignore-scripts` still runs `prepare` for git and folder dependencies on npm 10. The hand-off is `npm ci --ignore-scripts`, so no new or changed package runs code as it installs; `npm rebuild ./node_modules/<name>` then runs install scripts only for entries the base lockfile had at the same path with the same name, version, `resolved` and integrity. It is given paths because `npm rebuild <name>@<version>` also matches any package installed under that folder name deeper in the tree (a canary shows it). A project `.npmrc` with `git=` or `script-shell=` is overridden by the environment, which npm reads first. The hook doesn't start an npm or node from the project, its repository or a `node_modules` folder, or corepack's shim (which runs the npm `packageManager` names), judged on the PATH entry and on the real path it links to (only node's own `<prefix>/bin/npm` to `<prefix>/lib/node_modules/npm/bin/npm-cli.js` link is allowed into `node_modules`), requires npm 10 or 11, removes `NODE_OPTIONS`, `NODE_PATH` and `NODE_REPL_EXTERNAL_MODULE` from every npm it runs, and passes the loader's settings (`LD_PRELOAD`, `LD_AUDIT`, `LD_LIBRARY_PATH`, `DYLD_*`) only as Garnet started with them (`runner.LOADER_PRELOAD`); an npm install whose command line sets or changes one, or `GCONV_PATH`, `LOCPATH` or `PATH`, asks, and so does one that runs an npm other than the one the hook's own `PATH` finds or the npm installed with that `PATH`'s node. npm's subcommand is read as npm reads it (aliases, abbreviations, camelCase, `--`); any npm command not known to install nothing asks, and so does a command that takes packages (`docs`, `view`, `owner ls`, `publish`, …) naming one that isn't a registry release, since npm 10 fetches it and runs a git package's `prepare`, npx or `npm exec` starting a package manager, and node running npm's own files (`node ./node_modules/npm/index.js`). Residual: node started on npm's code by a path that hides it (a link named `x.js`, `cd node_modules/npm && node .`, `node -e`) isn't recognised. Residual: on a case-insensitive file system `NPM i x` runs npm, and the hook's fast path doesn't see it. |
| A hostile command line makes the hook run something | The hook parses the command with `shlex` and never runs it; only the pip or uv command it recognized runs, rebuilt as an argument list. Substitutions, variables, `eval`, here-documents and nested shells make the command "can't tell" (ask or deny), never a pass. A pip environment, uv, npm or Python that git tracks in the repository isn't started, since the hook runs before the user approves the command: that covers the interpreter pip's `--python` names, and uv's `-p`/`--python`, `UV_PYTHON` and `.python-version`. Nor is one that is inside the project and untracked (a `bin/uv` or `bin/pip`, by its path or the real path a link leads to), unless it is in the project's `.venv` or an active `VIRTUAL_ENV` that has a `pyvenv.cfg` and isn't the project folder. A command that sets `LD_PRELOAD`, `LD_AUDIT`, `LD_LIBRARY_PATH` or any `DYLD_` name for pip or uv is can't check, and the check's own pip and uv calls get those settings only as Garnet started with them (`runner.LOADER_PRELOAD`), so a library the command names never loads before the user approves it. A command that changes where uv finds a Python (`PATH`, `HOME`, `XDG_DATA_HOME`, `UV_PYTHON_INSTALL_DIR`, `UV_PROJECT_ENVIRONMENT`, `UV_PYTHON_PREFERENCE` and the rest in docs/install-wrapper.md) or pip's `PATH`, other than activating a venv, is can't check, and so is a relative or empty `PATH` entry; with no `.git` or `pyproject.toml`, the working folder is the project. `declare`, `typeset`, `readonly`, `local`, `builtin`, `set -a` and `export -n`/`-f` make the command can't tell, since the parser doesn't follow what they set. `GCONV_PATH` and `LOCPATH` set by the command are can't check too. Every program the check starts (and pip's script) must be what the hook's own `PATH` finds for its name, by real path, or in a virtual environment (`pyvenv.cfg`) that is the project's `.venv`, the hook's own `VIRTUAL_ENV` or outside the project; a program the command names anywhere else is can't check. Accepted: a `.venv`, the hook's `VIRTUAL_ENV`, and a venv outside the project, planted or not, are trusted as the user's own. |
| The hook can't see an install | Scripts, Makefiles, aliases and functions defined by an earlier command (`./setup.sh`, `make deps`) are not visible: the hook reads the command line only. On Codex, input written into a running process doesn't run hooks again. `uv run` in a project Garnet can't resolve (a workspace, dynamic metadata, local sources) gets a "not checked" note, and its sync runs unchecked. Accepted gaps, documented in docs/install-wrapper.md. Compound commands, function bodies, shell options before `-c`, a pipe into a shell, `python -m uv`, a program Garnet doesn't follow with `pip install` among its arguments, a program name the shell expands (`$P install x`, `$(command -v pip) install x`), and `uv run` of a script from a URL, stdin or a `--directory` are read or are can't tell, never silent. |
| The hook fails and the command runs unchecked | Claude Code: the printed configuration sets `onFailure: "block"`, so a crash or timeout blocks. Codex has no such setting and lets the call through on a crash, a timeout or invalid output, so Garnet answers by its own 240-second deadline and turns every internal error on a package command into a deny. A failure before Garnet's code runs (no Python, a broken install) still fails open on Codex, and so does any output from the user's login profile on stdout, since Codex runs the hook with `$SHELL -lc` and can't read the answer then (docs/install-wrapper.md says how to test it). |
| What the agent installs differs from what the hook checked | The agent's command resolves again, with builds on. Garnet compares each requested package with the newest matching release, so the common case (a newer release that needs a build) is "can't check", not a pass. A release published between the check and the install isn't covered; the wrapper, which installs exactly what was checked, is. |
| The wrapper writes over a project file someone changed during the check | uv's checked `pyproject.toml` and `uv.lock`, and npm's `package.json` and lockfile, are written back only if every copied file still has the hash it had when copied; otherwise nothing is written or installed (exit 3). The same test runs before `uv sync --frozen` and `npm ci` when there is nothing to write, so they install from the files that were checked. |
| Index credentials leak into output | Values from pip's configuration are never printed. The credentials in a URL (`https://user:token@host`) are shown as `****` in everything Garnet prints or writes, the command line and pip's, uv's and npm's error output included; nothing from `.npmrc` is printed, only the names of the npm settings Garnet refuses; the package manager still gets the URL as written. The temporary copy (mode 0700) is deleted after the run, and the hook deletes it before its deadline answer too. |

### Privacy

Garnet sends only what it needs to public registries and GitHub (package names, versions, file names). It has no telemetry. The hosted app, when it exists, will document exactly what it stores.
