# Changelog

All notable changes to Garnet Guard. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow semantic versioning from 1.0 (SPEC §12).

## Unreleased

### Added

- `garnet check` reads npm lockfiles: package-lock.json and npm-shrinkwrap.json (lockfileVersion 1, 2 and 3) and Yarn 1 yarn.lock, and so does the Action with `lockfiles: auto` (the example workflows' `paths` filters don't list the npm lockfiles yet). Every installed package counts, dev, optional and peer dependencies included, and each finding points at the entry's line: its key in package-lock.json, its `version` line in yarn.lock. An alias (`npm:real@range`) is checked as the package it installs. An entry counts as a registry release when its `resolved` URL is that package's tarball for that version on registry.npmjs.org or registry.yarnpkg.com, with a SemVer version, or when it has a version and an integrity but no URL (npm's `omit-lockfile-registry-resolved`). A registry URL for any other tarball, git, `file:`, other tarball URLs, private registries, a package bundled inside another one (`inBundle` with no URL or integrity of its own, reported as "bundled in <package>, checked only as part of it"; a flagged entry that has a URL is judged by it, since npm fetches it from there when the parent's tarball doesn't hold it) and a name that breaks npm's naming rules are GRN-E005; an invalid name is shown as `(invalid name)`, never echoed. A new integrity at the same URL counts as a change. The project, workspace members, links and yarn.lock entries whose patterns are all `link:` are skipped. package-lock.json's `packages` and `dependencies` sections are both read whatever `lockfileVersion` says, since npm 7 and later install from the first and npm 6 from the second; an entry the second installs differently is reported too. yarn.lock is read with a port of Yarn 1's own parser, and a file yarn would read some other way is refused with exit code 3: one its parser rejects (yarn then reads it as YAML), one with a line yarn stops reading at, one with merge conflict markers, and one with a `__metadata` entry. npm versions are ordered by SemVer 2.0 precedence when Garnet picks the baseline. `garnet check` finds package-lock.json, npm-shrinkwrap.json, yarn.lock and pnpm-lock.yaml after the Python lockfiles. A lockfile larger than 64 MiB is refused with exit code 3 too.
- `garnet check` reads pnpm-lock.yaml (lockfileVersion 9.0, from pnpm 9 and 10, and 6.x, from pnpm 8) and yarn.lock from Yarn 2 and later (`__metadata` version 4 to 8), and so does the Action with `lockfiles: auto`, which now looks for pnpm-lock.yaml too. Each finding points at the entry's key line. In pnpm-lock.yaml every `packages` entry counts, under the name and version in its key: a snapshot's peer or patch suffix is the same package, a patched dependency (`patchedDependencies`) is checked as the release it patches when the patch file the lockfile records is in the project, and is GRN-E005 "patch file outside the project" otherwise, and an alias is checked as the package it installs. An entry with only an integrity is the registry release of that name and version; a `tarball` URL must be that package's registry tarball for that version. Git, directory and other tarball sources, and `@jsr/` packages (which pnpm fetches from npm.jsr.io unless the settings name npm's registry for them), are GRN-E005; `link:` and workspace dependencies have no entry and are skipped. A pnpm-lock.yaml from pnpm 7 or earlier (lockfileVersion 5.x) is refused with exit code 3, saying to regenerate it with pnpm 8 or later, and so is a shape pnpm doesn't write (a snapshot with its own resolution, or with no `packages` entry; a `version` that disagrees with the key). In a Yarn 2+ yarn.lock, a `name@npm:<version>` resolution is checked, an alias as the package it resolves to; `workspace:` entries, and `link:` and `portal:` folders inside the project, are skipped. `patch:` is checked as the release it patches when every patch file is in the project or built into Yarn (`builtin<compat/...>`, written `optional!builtin<...>` by Yarn 4 and `~builtin<...>` by Yarn 2 and 3), and is GRN-E005 "patch file outside the project" otherwise, whatever it patches. A `@jsr/` package in a Yarn 4 lockfile is GRN-E005 unless .yarnrc.yml configures the `jsr` scope, since Yarn 4 fetches it from npm.jsr.io. `file:`, `exec:`, git, other tarball URLs, and `link:` or `portal:` outside the project, are GRN-E005. A new commit, URL, folder, integrity or checksum for an entry Garnet can't check counts as a change. Neither format records which registry a package comes from, so Garnet reads the settings beside the lockfile: `registry` and `@scope:registry` in .npmrc (read the way pnpm's `ini` parser reads it) and `registries` in pnpm-workspace.yaml for pnpm, and `npmRegistryServer` and `npmScopes` in .yarnrc.yml for Yarn 2+. A package they send anywhere but registry.npmjs.org or registry.yarnpkg.com, including to a registry named by an environment variable, is GRN-E005 "private registry, set in <file>"; a key naming an environment variable (`${X:-registry}`, which pnpm expands) counts as every registry key it may be read as. Nothing else in those files is read and nothing from them is shown; a settings file that is a symlink is refused like a lockfile, and the strict YAML reader applies only to the keys Garnet reads, so a pnpm catalog may use anchors. Both formats are read with a strict YAML reader (`lockfiles/yamldoc.py`) that refuses anchors, aliases, tags, merge keys, repeated keys and plain values YAML 1.1 and js-yaml's YAML 1.2 read differently, with exit code 3 and a line number, never the file's text. A yarn.lock counts as Yarn 2+ only when its first entry is `__metadata:` with a `version` under it, the shape Yarn 1 ignores, so a yarn.lock that switched from Yarn 1 since `--git-base` is read on both sides.
- PyYAML (`pyyaml>=6.0.2`) is a runtime dependency, used only through its parser's events, never a loader (ADR-0016).
- `garnet pip install …` and `garnet uv add|remove|lock|sync …` check a dependency change before it is installed, then install exactly what was checked (SPEC §10.3, [docs/install-wrapper.md](docs/install-wrapper.md)). The change is resolved with builds turned off: pip's `--dry-run --report` with `--only-binary :all:` after every argument, and uv with `--no-build` and `UV_NO_BUILD=1` in a private copy of `pyproject.toml`, `uv.lock`, `uv.toml` and `.python-version`. Every requirements file is read first, uv's `-r` and `-c` files too, and anything that would build or that Garnet can't compare is refused as not checked: `--no-binary`, editable installs, paths and archives (read as pip reads them, so `x.tar.gz[a]` and `x.tar.lzma` count), URLs, VCS requirements, uv's `--build`, workspaces, path, git, URL or editable sources and direct references, and pip settings that add requirement files. uv never downloads a Python while checking (`--no-python-downloads`), since a project can name where downloads come from, and a non-index package in the resolved `uv.lock` is not checked. The base is `pip inspect` for pip and the `uv.lock` committed at `HEAD` for uv. Below `fail_on`, pip installs with `--only-binary :all: -c <pins with sha256>` and uv writes the checked files back (only if neither changed meanwhile, else exit 3) and runs `uv sync --frozen`; at or above it nothing is installed (exit 1 or 2). A package manager that fails after the check exits 3, never 1 or 2. With builds off, pip and uv fall back to an older release when the newest needs a source-only dependency (num2words resolves to 0.5.6 instead of 0.5.14, which needs docopt); Garnet compares each requested package with the newest matching PyPI release and reports that case as not checked, with what needs a build, what resolved without building and the options, and installs nothing (exit 3). `--garnet-force` installs anyway. Two tests run real pip and uv, offline, against source distributions whose build backend doesn't exist, and show that the plain command tries the build and Garnet's resolve step doesn't.
- `garnet hook claude-code` and `garnet hook codex` print a PreToolUse hook configuration, and `garnet hook <agent> run` answers one hook event (SPEC §10.4). The hook reads the shell command with `shlex`, never runs it, and checks each pip and uv command in it with the wrapper's resolve-and-check step; it never installs. Pass and warn return the findings as `additionalContext` with no permission decision; findings at or above `fail_on` deny with the findings; a command it can't check or can't read (substitutions, variables, `eval`, here-documents, a pipe into a shell, PowerShell) asks on Claude Code, with the same text in `additionalContext` for the agent, and denies on Codex, which has no `ask`; `uvx`, `uv tool`, `uv run --with` and poetry are not checked and ask or deny the same way; npm, pnpm, yarn and `uv pip` get a note that the install wasn't checked. `uv run` is checked as the `uv sync` it starts with, and gets no answer when that would install nothing new. It answers within 240 seconds, keeps every text field under 8,000 bytes, writes the full report to a file only when the answer leaves something out (findings or a cut field: Claude Code's scratch folder, else the system temp folder), and doesn't start a pip, uv or Python that git tracks in the repository, including one named by `--python`, `-p`, `UV_PYTHON` or `.python-version`. A command with no package-manager word returns in about 35 ms (median of 20 runs here, against about 800 ms when the engine loads): the entry point is now `garnet_guard.console:main`, which sends `hook <agent> run` to a gate that imports only the standard library, and `garnet_guard` loads its public names on first use.

### Changed

- GRN-C009 compares targets across the whole group, not name by name, in the groups whose tool loads every line's target whatever its name: `pygments.lexers`, `keyring.backends`, `setuptools.file_finders`, `setuptools.finalize_distribution_options`, opentelemetry's pre- and post-instrument hooks, `pdm` and the poetry plugin groups. A line that gives a target the trusted version already listed in the group a new name runs nothing new and is not reported; mako 1.4.1, which renamed its lexers `css+mako` to `css_mako` and so on with the same classes, warned for four "new" entry points and is now `info` for the extras its two extractors dropped. A renamed line that loads another object still warns. Groups where the name decides what runs (`distutils.setup_keywords`, `egg_info.writers`, `pydantic`, `opentelemetry_instrumentor`, flake8, virtualenv) and the other `setuptools.*` groups, not known to ignore it, still compare name by name.
- Lockfile errors name the lockfile, and say when the problem is in the base version.
- `garnet diff npm:<name>` accepts every name npm's rules allow, including older names with `~`, `!`, `*`, `'`, `(` or `)` or a leading `-`, and refuses names with `..`. The npm lockfile parsers apply the same rules, so a name they pass is one the registry adapter accepts.
- GRN-E005's explanation says Garnet compares releases published on PyPI and npm (it said PyPI), and lists private registries and bundled npm dependencies among the sources it doesn't check.
- GRN-C003 reads an undecorated `def` as rebinding its name for the rest of the block it is in, so a call there after it names the function just defined, not an alias the name held earlier in the file. mpmath 0.18's copy of `six` defines `exec_` in its Python 2 branch and calls it at once; the finding listed that call as calling `builtins.exec`, the value `exec_` gets in the Python 3 branch. It now lists only the `exec` inside `exec_` that the call reaches, and still warns. After the `if`, loop or `try` holding the def, a call to the name is still reported as a call to the alias, and a decorated def or one whose default arguments call the alias unbinds nothing. Only the evidence of findings like mpmath's changes; on the standard library and this repository's own dependencies the calls indexed are identical. On the 144 PyPI top-1,000 packages with a GRN-C003, C002, C007, C010 or C012 finding in 0.2.0, no finding or severity changes (litellm and sympy still measuring), and the 52 replays still warn. The backtest cache format is 50.

### Fixed

- The agent hooks started pip or uv with a `LD_PRELOAD`, `LD_AUDIT`, `LD_LIBRARY_PATH` or `DYLD_*` setting the command line gave (`LD_PRELOAD=./pre.so uv add six`), so the library it named loaded before the user approved the command. Such a command is "can't check" now (ask on Claude Code, deny on Codex), with the setting named, and the check's own pip and uv calls, in the wrapper too, get those settings only as Garnet itself started with them.
- The agent hooks started a pip or uv inside the project that git doesn't track (an untracked `bin/uv`, a `bin/pip`, or a link to one) to check the command, before the user approved it. Only a committed one was refused. A program whose path or real path is inside the project (the nearest `.git` or `pyproject.toml` folder) is "can't check" now, unless it is in the project's `.venv` or the active virtual environment.
- The agent hooks started a pip, uv or Python the command named by a path outside the project (`/tmp/x/uv add six`, `uv sync -p /tmp/x/python`, `UV_PYTHON=/tmp/x/python`), before the user approved the command. A program now has to be what the hook's own `PATH` finds for its name, or in a virtual environment (the project's `.venv`, the hook's `VIRTUAL_ENV`, or one outside the project); anything else is "can't check". A command that sets `GCONV_PATH` or `LOCPATH` is "can't check" too.
- The agent hooks let uv start a Python the command chose before the user approved it: a planted interpreter under `UV_PYTHON_INSTALL_DIR`, `XDG_DATA_HOME`, `HOME` or `UV_PROJECT_ENVIRONMENT`, or `python3` on a `PATH` the command set, and pip a Python found through a `PATH` the command set. A command that changes these, or a relative `PATH` entry, is "can't check" now; activating a virtual environment is still checked. A program in a folder with no `.git` or `pyproject.toml` counts as that folder's own, and `declare`, `typeset`, `readonly`, `local`, `builtin`, `set -a` and `export -n` make a command "can't tell".
- GRN-C008 read only the first declaration of a dependency's name. A second one, such as `"h2": "npm:young@^1"` in `optionalDependencies` (which npm lets override `dependencies`) beside `"h2": "npm:established@^1"`, a `github:`, URL, path or `file:` source there, or a second `Requires-Dist` line with a direct URL, installs a target Garnet never looked up, and the finding could be `info`. The rule now keeps its `warn` severity for it, names that target and says Garnet didn't look it up; for a dependency the trusted version already had, when the target is new. The backtest cache format is now 49.
- GRN-C010 matched only files named `sitecustomize.py` and `usercustomize.py`. It now matches the top-level module name in any case, so a `sitecustomize/` package, a `.pyc` with no source, an extension module (`.so`, `.abi3.so`, `.pyd`) and `SiteCustomize.py` warn too, at the top of site-packages, under `<name>.data/purelib/` or `platlib/`, and below a `site-packages` or `dist-packages` folder under `<name>.data/data/`. A `__pycache__/sitecustomize.*.pyc` with no source isn't imported and stays quiet.
- GRN-T002 treated a repository as the trusted one when its repository id matched, whatever the host. Fulcio puts GitLab project ids in the same certificate extension as GitHub repository ids, so a GitLab project with the same number as the trusted GitHub repository stayed quiet. An id now counts as a rename only on the same host (compared case-insensitively).
- A requirements file's `--index-url` (`-i`) applied only to the lines after it, and abbreviated or attached options (`-ihttps://…`, `--index=…`, `--extra-ind URL`, `-f/dir`, `--find-l=/x`, `--no-ind`) weren't read, so a pin could be checked against PyPI while pip installed it from another index. Options are now read as pip 24 reads them and apply to the whole file: a file that sets an index other than PyPI, an extra index, `--find-links` or `--no-index`, or holds an option pip would refuse, reports every `==` pin in it as GRN-E005, naming the option, never its value. `garnet check` follows `-r` and `-c` files as pip resolves them, inside the directory it checks, never through a symlink and at most 10 deep, in the working tree and at the base, and applies the index options of the whole include tree to every pin in it; an include it can't follow (a URL, a `..` part or a path outside the directory, missing, a symlink, a cycle, too deep, more than 100 includes or 64 MiB in one tree) leaves the tree's pins as GRN-E005. Lines are joined and comments stripped as pip 24.0 does (`--\` then `index-url …` is `--index-url …`), for the install wrapper's requirements reading too, and an option pip would refuse is named only by its leading letters, never a value glued to it. `--hash` and other options that don't change where pip installs from keep pins checked.
- The text report wrote a line break inside a lockfile version, or any other field, as a new line, so the rest could pass for a line of the report. It is shown as `\x0a` now, like other control characters.
- `--policy-change` compared ignore names PEP 503 normalized whatever the ecosystem, so an ignore moved from `foo_bar` to `foo-bar`, two different npm packages, wasn't listed. Only an ignore with `ecosystem = "pypi"` is compared normalized now; matching already compared npm names exactly.

## 0.2.0 (2026-10-31)

The first full release, for launch. It adds seven content and trust rules to the ones in 0.1.0a1, widens the sensitive call set, and reads the wheel pip would install. With every rule it ships, the backtest warns on all 52 replayed malicious releases (47 PyPI, 5 npm), and flags 606 of 18,181 everyday updates of the top 1,000 PyPI and npm packages for a look (3.3%), none a false claim. An ignore now expires within 12 months, so a policy with a longer `until` has to shorten it (Changed, below).

### Added

- GRN-C004 new-binary, on PyPI. Garnet reads each file's first bytes, so ELF, Mach-O and PE code counts as native whatever the file is called. The rule warns for native code under a name whose last extension says otherwise (num2words 0.5.15 shipped a Windows DLL as `_build.py`; GPU code objects such as `.cubin` and `.hsaco`, and `.node` addons, count as native names), for any native code when the trusted release shipped none, including a file that becomes native code, for a `.pyc` that Python imports with no source beside it, including one whose `.py` the new version removed (pytest's assertion cache, `test_x.cpython-313-pytest-8.4.1.pyc`, isn't imported and isn't reported), and for a hash-based `.pyc` (PEP 552), checked or not, that Python loads in place of its source without comparing its code. A new library in a new folder of a release that already shipped native code is reported at `info`; rebuilt binaries, new libraries in a folder that already held native code, and new extension modules of a compiled release are not reported. On the 974-update PyPI corpus it reports nothing. Among the 52 replayed malicious releases it adds a warning to num2words 0.5.15 and 0.5.16 and memoryos 2.0.34, each already warned by another rule. An archive Garnet can't read to the end now names GRN-C004 among the rules not evaluated.
- GRN-C008 new-dependency, on PyPI and npm: the new version declares a dependency the trusted version didn't, or a dependency it had now installs from somewhere else. Garnet asks the registry when each new dependency was first released, how many releases it has, which repository it names and which accounts own it. It warns when the dependency isn't on the registry, installs from git, a URL or a path, or was first released less than 90 days before the new version, even when the trusted package's owner owns it too (the evidence says so); any other new dependency is reported at `info`. Dependencies are read from the wheel's `METADATA`, or from an sdist's `PKG-INFO` when it is metadata 2.2 or later and doesn't mark them dynamic, and from `package.json` on npm, with `npm:` aliases resolved to the package they install. When an npm name was unpublished and created again, the evidence calls the date the earliest version still published and names the removed versions (call-bound's 1.0.0 of June 2024, for one). A failed registry lookup is GRN-E001. The npm backtest replays event-stream 3.3.6 (2018), which added `flatmap-stream`; 52 of 52 malicious releases replayed now get a warning. On the 974-update PyPI corpus it adds no warning and 18 `info` findings; on the 1,809-update npm corpus it adds 19 warnings, each a young dependency, 14 of them published by the trusted package's own maintainer.
- `garnet check --git-base REF --policy-change PATH` lists what the working tree changes in a policy file since `REF`, loosening changes first (a new or extended ignore, a rule lowered or turned off, `fail_on` raised, a limit raised, the file deleted). The JSON report carries it as `policy_changes` and the PR comment opens with a callout. The Action passes its policy file, so a pull request that bumps a dependency and also edits the policy shows the edit; the pull request is still checked with the base commit's policy.
- GRN-T006 files-uploaded-late, on PyPI: a file of the new version was uploaded more than 24 hours after its first file. For each late wheel Garnet builds the machines the release's wheels are made for from their own tags, ranks the wheels on each in pip's order, and warns when a late wheel would be installed where an on-time file was: the release's first wheel, or a wheel that ranks above, ties with or has a higher build number than an on-time wheel on some machine. The evidence names that machine and the file. Late wheels that only add Python versions or platforms are reported at `info`. On the 974-update PyPI corpus it adds 2 warnings (cffi 1.14.5, whose aarch64 wheels were uploaded again 96 days later with the same tags, and iniconfig 1.1.1, whose only wheel arrived two days after the sdist) and 11 `info` findings; the 52 replayed malicious releases are unchanged.
- A change whose trusted release has no attestation and no git tag carries a note saying so: GRN-T001 to GRN-T005 compare with one of those, so they had nothing to compare with. The note is in the text report, the JSON report (`notes`, only when there is one) and the PR comment ("publishing not compared"), and never changes a verdict. On the 974-update PyPI corpus 84 updates carry it, and 15 of the 52 replayed malicious releases.
- GRN-C003 lists, in a separate finding at `info`, new reads at import of environment variables that hold credentials or say the code runs in CI (`GITHUB_TOKEN`, `AWS_*`, `CI`, …), of the whole environment, and of cloud metadata addresses. It adds no warning: on the 974-update corpus it lists one read (tqdm 4.68.2), and among the replays it lists reads in mistralai 2.4.6, memoryos 2.0.34 and mrmustard 0.7.4, each already reported by a warning.
- GRN-C009 new-entry-point, on PyPI wheels: the new version's wheel declares an entry point the trusted version's didn't, or points one at a different target. Garnet reads entry points as `importlib.metadata` does on Python 3.11 to 3.14: the `entry_points.txt` of each `.dist-info` or `.egg-info` folder at the wheel's root or under `<name>.data/purelib/` or `platlib/`, names matched ignoring case; only `#` starts a comment, so `;demo = x` is an entry point; `[[pytest11]]` is the group `pytest11`; and a name listed twice keeps both targets, with the evidence saying which one pip, pytest or setuptools runs. A new target for a name is reported, and so is a line that now runs where it didn't: a script's last line in the wheel's own file, or, for `pytest11`, `tox`, `hatch` and groups looked up by name, a target newly first in an `entry_points.txt`. In a group whose tool loads every line (`setuptools.*`, `egg_info.writers`, `flake8.extension`, `keyring.backends` and others) only a new target counts. Lines removed, repeated or reordered with nothing new running are not reported. It warns for a group another tool loads by itself, where the target runs inside that tool in the environment the package is installed in (`pytest11` in every pytest run, `setuptools.*` in builds that don't isolate themselves, `flake8.extension`, `keyring.backends` and others), and for a new script in the wheel's own `entry_points.txt` with a common command's name (`pip`, `git`, `curl`, …) other than the project's own; any other new or changed entry point is `info`. Entry points that warn lead the evidence, and the evidence says how many more there are. A wheel Garnet couldn't read to the end is not compared, and its GRN-E002 or GRN-E003 (or GRN-E001 for a failed download) names GRN-C009 among the rules not evaluated. On the 974-update PyPI corpus it adds 1 warning, accurate (platformdirs 4.12.0 adds a `pytest11` plugin), and 6 `info` findings (new or moved console scripts in cffi, charset-normalizer, idna, pytest, websockets and wheel). No replayed malicious release adds or changes an entry point, so the replays are unchanged.
- GRN-C010 new-startup-file, on PyPI wheels: the new version's wheel adds a file that runs or installs outside the package. That is `sitecustomize.py` or `usercustomize.py` at the top of site-packages, which Python imports at every start, a script under `<name>.data/scripts/`, which becomes a command, or a file under `<name>.data/data/`. It warns for the two startup modules, for a script named like a common command (`pip`, `git`, `curl`, …) and for a file installed under `etc/`; other scripts and data files are `info`. On the 974-update PyPI corpus it adds no warning and 1 `info` finding (jmespath 0.9.2's `jp` script); the 52 replayed malicious releases are unchanged.
- GRN-C012 wheels-differ, on PyPI. The content rules read one wheel, the one pip would install where Garnet runs. GRN-C012 also downloads one wheel per other platform family (Windows, macOS, Linux, pure Python, other) and every wheel uploaded more than 24 hours after the release's first file, up to 30, checks each against PyPI's hash, and parses (never runs) each Python file that differs from the read wheel's copy. It warns for a sensitive call (§6.3) the read copy doesn't make and none of the trusted version's wheels for that platform family made in that file, the one Garnet read included. When the read copy doesn't parse (a Python 2 file in an old `cp27` wheel), the call is compared with the trusted version's wheel for that family; with nothing to compare it warns as well, and only beside a GRN-E002 warning for that read copy is it listed at `info`. A differing file Garnet can't parse is GRN-E002 naming GRN-C012, unless a trusted wheel of the same platform family had the same bytes at that path, and one over the 5 MB parse limit GRN-E003 naming it; a top-level module named like a standard-library module, a builtin or another name the sensitive call set starts with (`subprocess.py`, `exec.py`, `requests.py`) doesn't make those calls the package's own. Late wheels past the 30th aren't compared, and that is GRN-E003 naming GRN-C012 with the wheels listed, so the update doesn't pass. On the 974-update PyPI corpus no release has more than 20 late wheels (pillow 11.3.0 has 20, lxml 6.0.0 has 19), so none reaches the cap. `garnet explain GRN-C012` prints the sensitive call set. On the 974-update PyPI corpus it compared other wheels in 304 of 1,074 releases, all in the 28 packages that ship platform wheels, and adds no warning and 2 `info` findings (PyYAML 5.3.1 and 5.4, read through `cp27` wheels). It costs 3.35 GB of extra downloads on top of 4.23 GB (79% more), a median of 0.9 MB for each release that has other wheels. No replayed malicious release ships more than one wheel, so it reports no difference on the replays. In the ensmallen 0.8.101 replay, the read wheels of both versions are over a limit, so their existing GRN-E003 lines also name GRN-C012, and no line is added.
- GRN-C011 new-js-capability, on npm, at `info`: the JavaScript a package loads uses a module or global the trusted version's didn't. That is `child_process`, `cluster`, `worker_threads`, `net`, `dgram`, `dns`, `http`, `http2`, `https`, `tls` or `vm`; `eval`, `Function` or `fetch` called; `XMLHttpRequest` or `WebSocket`; or 20 or more `_0x` names in one file, the shape javascript-obfuscator writes. The files are those `package.json` names as entry points and every file they load through a relative `require` or `import`. A tokenizer in `facts/jsscan.py` skips comments, strings, template text and regular expressions, adds no dependency and runs nothing; each use says whether it runs when the file loads. A loaded file over 16 MB, a new §4.4 limit, is GRN-E003. On the 1,809-update npm corpus it adds no warning and 5 `info` findings, each a real new use (agent-base 7.1.1 `net`, dotenv 18.0.0 `child_process`, function-bind 1.0.0 and json5 2.0.1 `Function`, source-map 0.7.0 `fetch`). The npm replays carry no tarball, so it can't fire on chalk 5.6.1 or debug 4.4.2; a fixture shaped like chalk's obfuscated line covers that case.

### Changed

- The §6.3 sensitive call set is version `2026-10-c`. It adds processes started without `subprocess` (`os.fork`, `os.startfile`, `asyncio.create_subprocess_*`, `multiprocessing.Process` and the `SpawnProcess`, `ForkProcess` and `ForkServerProcess` classes behind it, `_winapi.CreateProcess`, `_posixsubprocess`, `distutils.spawn.spawn`, `pydoc.pipepager`), code loaded from a file or built from a code object (`runpy`, `zipimport`, `importlib.__import__`, `importlib` file loaders and `spec_from_file_location`, the `imp` loaders such as `imp.load_source`, `types.FunctionType` and its alias `types.LambdaType`, `types.CodeType`), and more network clients (`asyncio` streams, `urllib3`'s pool managers, connection pools and connections, `ftplib`, `smtplib`, `poplib`, `imaplib`, `telnetlib`, `xmlrpc.client`, `webbrowser`). `subprocess`'s exception and result classes (`CalledProcessError`, `CompletedProcess`, `SubprocessError`, `TimeoutExpired`) and the function `subprocess.list2cmdline`, which set `2026-10-b` matched through `subprocess.*`, no longer count, because building them or quoting a command line starts nothing. A name under a module that defines or imports a listed one counts as that name (`builtins.exec`, `posix.system`, `ssl.create_connection`, `distutils.ccompiler.spawn`, `asyncio.subprocess.create_subprocess_exec`, `urllib3.poolmanager.PoolManager`, `_frozen_importlib_external.SourceFileLoader`), and a top-level module a release ships under a name in the set, such as an empty `os.py`, `requests.py` or `builtins.py`, no longer hides the calls to that name. For GRN-C003 and GRN-C007, only the `requests` project itself, named by its wheel or sdist filename, counts as calling its own `requests` code, and the same for `httpx`, `aiohttp`, `urllib3` and `setuptools`; GRN-C012 never counts these names as the release's own. GRN-C002, GRN-C003, GRN-C007 and GRN-C012 read the set, and `garnet explain GRN-C007` now prints it as well. On the 974-update PyPI corpus it adds no warning and 1 GRN-C003 `info` finding (a scipy 1.18.0 test helper that calls `types.FunctionType`). The replays are unchanged: each replayed payload already used a call that was on the list.
- When the new version is the first to ship a wheel and the trusted one shipped only an sdist, the content rules (GRN-C001, GRN-C003, GRN-C004, GRN-C008 and GRN-E002) compare both the new wheel and the new sdist with the trusted sdist, and report a finding the two share once. They used to compare only the two sdists, so a payload only in the wheel, which pip installs wherever it fits, went unread. A comparison of a wheel with an sdist ignores the sdist's `src/` folder and says so in a note, and GRN-E002 now carries that note too. On the 974-update PyPI corpus 4 updates are read both ways and no finding changes; one GRN-E002 finding (PyYAML 5.4) gains the note that its wheels have different tags. No replayed malicious release has this shape.
- An ignore whose `until` is more than 12 months after the day the policy is read is refused (exit code 3), with the latest date accepted. An ignore records a review, and a review goes out of date. A policy with a longer `until` must shorten it before this version will run.
- Content rules read the wheel pip would install on the machine Garnet runs on (SPEC §4.2). A pure-Python wheel used to be read first whenever there was one, so a platform wheel added beside it went unread.
- The remediation text of GRN-T002, GRN-C001 and GRN-C003 points at the repository first (the commit, the tag), because whoever published a release also wrote its release notes. GRN-C003's says that a condition around a new call, such as running only in CI, is evidence, not reassurance.
- GRN-C007 reads a published file back and indexes its calls only when the file isn't in the source tree, after the tag lookup, instead of indexing every file at inspection. A release from a large repository (transformers ships 5,600 Python files) costs one hash per file and one tree fetch, not a second parse of everything.

### Fixed

- When no wheel of a release fits the Python Garnet runs on, as for a release older than it, the content rules read the wheel for this machine's platform built for the newest CPython, then for x86-64, then the first by name (SPEC §4.2). They used to read the first wheel by name, which could be a Python 2 build of one release and a Python 3 build of the next. On the top-1,000 PyPI corpus GRN-C004 said pendulum 2.0.5 added two compiled files that 2.0.4 didn't have, though 2.0.4's Python 3 wheels have the same two files, because 2.0.4's first wheel is a Python 2 build with no compiled code; and it warned on pendulum 3.0.0's new extension module for the same reason, though 2.1.2 already shipped compiled code.
- GRN-C007 said code was not in the repository when it was. On the top-1,000 PyPI corpus it warned on 9 updates, and in 4 of them every flagged file is in the source. sympy/sympy tags 1.12.1 twice, as `1.12.1` and `sympy-1.12.1`, at different commits, and the wheel was built from the second. multiprocess 0.70.12.1 ships only Windows wheels, whose files have CRLF line endings. pycryptodomex 3.17 and 3.19.1 publish pycryptodome's `lib/Crypto/` as `Cryptodome/`. GRN-C007 now reads CRLF as LF, compares a package published under another name with the folder it came from, and tries every tag that names the version when the first leaves a sensitive call unexplained. The other 5 warnings were unchanged by the fix: daff 1.4.2, nodejs-wheel-binaries 24.11.1 and 24.19.0, shellingham 1.2.8 and tensorboard 2.20.0 ship files that are in no tree at the tag. With sensitive call set `2026-10-c` (above), nodejs-wheel-binaries 24.11.1 no longer warns, since its only call was `subprocess.CalledProcessError`, and daff 1.3.45 does, for a generated file that opens a web browser; the final top-1,000 run has 5 GRN-C007 warnings.

## 0.1.0a1 (2026-10-30)

The first pre-release. It claims the `garnet-guard` name on PyPI and lets people try the command line before the first full release. Expect changes before 0.2.0.

### Added

- `garnet diff <package> <old> <new>` compares two PyPI releases (npm below). It reads PEP 740 provenance (verified with Sigstore), git tags, OSV malicious-package advisories, and the contents of the sdist and one wheel.
- `garnet check` compares two lockfiles (`--base` and `--head`, or `--git-base <ref>` for every lockfile against the same files at that commit) and checks every package that changed. It reads uv.lock, poetry.lock, pylock.toml and requirements files.
- Rules:
  - trust: GRN-T001 to T005, T007 and T008
  - content: GRN-C001 to C003 and C007
  - known-bad: GRN-K001
  - couldn't-check: GRN-E001 to E005
- `garnet explain <RULE-ID>`, text and JSON reports, and exit codes per SPEC §8. The command is `garnet`; `garnet-guard` is the same command, so `uvx garnet-guard` works (ADR-0007).
- `python -m backtest` replays real incidents and a clean corpus. The incidents are 47 malicious releases of 36 compromised PyPI packages (Dec 2024 to Sep 2026) and four npm account takeovers. All 51 get a warning. Each is checked against the git tags as they stood when it was uploaded, and against attestations where public sources confirm a release had none.
- A docs page for every rule ID in `docs/rules/`, with an example finding and how to resolve or allowlist it. Findings, `garnet explain` and the PR comment link to these pages on https://garnetguard.dev/rules/.
- CI on every pull request (ruff, mypy, import contracts, tests on Python 3.11 to 3.14, build), the OpenSSF Scorecard workflow, Dependabot for the repository itself, and a tag-triggered release that publishes to PyPI with Trusted Publishing and PEP 740 attestations. See docs/RELEASING.md.
- The GitHub Action (`action.yml`) checks a pull request's lockfile changes and posts or updates one comment. It includes a `workflow_run` comment job for forks (`action/comment`) and example workflows in `action/examples/`. See docs/action.md.
- `garnet check --format markdown` and `python -m garnet_guard.markdown` render the PR comment (SPEC §9.4) from a report.
- The policy file (SPEC §7): `garnet.toml`, or `[tool.garnet]` in `pyproject.toml`, sets rule severities and `fail_on`, lowers the input limits, and holds expiring ignores for findings someone has reviewed. `garnet check` and `garnet diff` read it (`--policy PATH`, `--no-policy`), `garnet policy check` validates it, and the Action's `policy` input reads it from the pull request's base commit. Ignored findings stay in the reports with `suppressed_by`; expired ignores are reported. See docs/policy.md.
- `garnet check --format sarif` and `python -m garnet_guard.sarif` render a SARIF 2.1.0 report (SPEC §9.3) for GitHub code scanning, with one alert per finding on the lockfile line that pins the new version. The Action's `sarif: true` input uploads it, so findings show in the pull request's changed lines and the Security tab.
- GRN-C007 code-not-in-source: a Python file in the new version's wheel (the sdist when there is no wheel) is not the file at the release's git tag, and it has calls that run processes, load code or use the network which the source file doesn't. The source tree is read over GitHub's git protocol on plain HTTPS (`ecosystems/gittree.py`): one request per tagged release, no token, no REST rate limit, and submodules hosted on GitHub are followed one level. It reports ultralytics 8.3.42 (Dec 2024), whose payload was injected by a poisoned CI cache and never committed, with 0 warnings on the 974-update clean corpus. `net.Http.post` sends raw bytes for it.
- npm: `garnet diff npm:<name> <old> <new>` compares two npm releases. It reads the registry's package document, npm provenance (verified with Sigstore, including the older `intoto` log-entry format that sigstore-python no longer accepts), git tags, OSV advisories and the tarball's `package.json`. The trust rules, GRN-K001 and GRN-T008 (Subresource Integrity) apply to npm; GRN-C002 reports an added or changed `preinstall`, `install` or `postinstall` script (not `prepare`, which npm doesn't run for a published tarball); GRN-T004 also accepts `<name>@X` tags. The backtest replays chalk 5.6.1, debug 4.4.2, nx 21.5.0 and @ctrl/tinycolor 4.1.1 from recorded registry facts, and `python -m backtest corpus npm` runs the top-200 npm clean corpus. npm lockfiles are not read yet.
- `python -m backtest select|corpus [pypi|npm] [SIZE]` runs a clean corpus of up to the top 1,000 packages, in worker processes (`GARNET_BACKTEST_WORKERS`). The top-1,000 PyPI and npm runs and their reports are in `backtest/corpus-results-pypi-1000/` and `backtest/corpus-results-npm-1000/`.

### Changed

These changed while the replays and the clean corpora ran, before the tag.

- GRN-T004 reads more tag forms: `X` or `vX` after a prefix that names the package or is `release`, joined by `-`, `_`, `==` or `/` (and `@` for npm), as in `release-v1.0.0`, `azure-mgmt-core_1.1.0` and `prebuilt==1.0.11`. A monorepo's folder or `==` prefix may use the end of the name (`api/v1.4.1`, `utils/v2.8.1`) when the repository never tags the package by its full name. The top-1,000 corpora found 16 releases that it wrongly said had no tag.
- GRN-T001 on npm says "no attestation served", with the HTTP status, when a version document lists an attestation that the registry's attestations endpoint doesn't serve (whatwg-url 17.1.1).
- GRN-C003 follows more of what runs at import: lambdas that are called or passed to a call, classes that are instantiated (their `__init__`) and methods called on them, names pulled in by `from os import *`, and `getattr(os, "system")`, `__import__("os")` or `importlib.import_module("os")` with a literal name. A `base64` decode whose result reaches `exec` or another sensitive call is reported as a call of its own, so a release that starts decoding what it executes is flagged even where `exec` was already used. Sensitive set version `2026-10-b`.
- GRN-C002 reads the whole of `setup.py`, not only what runs at import, so a `cmdclass` install hook that runs a command is reported (with the function it sits in). When the trusted version shipped no sdist, every build-time call in the new sdist is new; when the trusted sdist exists but couldn't be read, GRN-E001 reports that instead.
- GRN-C001 compares `.pth` files by where they land in `site-packages`: a file under `<name>-<version>.data/purelib/` is the same file release after release, a `.pth` deeper in the package (which Python never reads) is ignored, and a renamed `.pth` with the same `import` lines is not new. Modules under `.data/purelib/` keep their names across versions for GRN-C003.
- When the trusted version ships only a wheel and the new one only an sdist (or the reverse), the content rules compare the two kinds with each other and say so, instead of comparing nothing.
- GRN-C003 follows import-time calls into the package's own other modules, as deep as they go and through function-local imports, and names the module whose import started the chain. It also follows `sp = subprocess` style aliases and `getattr(sys.modules[__name__], "ctypes")`, the num2words 0.5.15 trick for reaching a module without naming it.
- GRN-C003 follows a function defined inside another function when it is called or handed to a call there, the mrmustard 0.7.4 shape: a checker run at import that started a thread on a `_run` nested inside it.
- GRN-C003 no longer makes four claims the top-1,000 PyPI corpus showed to be false: a dotted name whose first part is not an imported module (a local list called `requests`), a builtin shadowed by the module's own function or class (`def compile`), a module renamed with a leading underscore reported as new, and a module the trusted version had but couldn't parse reported as new (it now says the calls may not be new).
- GRN-C003 reports three more kinds of call at `info`, each in its own finding, instead of `warn`: a function that import-time code only handed to a call not known to run it (`functools.partial(f)`, a wrapper factory; the evidence now reads "handed to X() at import"), a call reached only from a test file that nothing imports, and a call in or reached only from an sdist file outside the package (`docs/conf.py`, `examples/`). Handing to `threading.Thread`, `atexit.register` or `executor.submit` still counts as running. A call that a package module reaches at import is reported once, at `warn`, whichever chain is followed first, and a module whose trusted copy couldn't be parsed is titled as such instead of "adds". A top-level `test/` folder counts as test files, like `tests/` (ply 3.6's `test/calclex.py`); one inside the package does not, because it is installed (`django.test`).
